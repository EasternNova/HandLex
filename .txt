Phase 1 — Consolidate V6 and V7
Start here · Required
Objective: Understand the existing experiments and select the strongest representation for production.
Task	What we are going to do
1.1	Study existing V6 and V7 analysis results, including feature importance, orientation, rotation sensitivity and validation findings.
1.2	Compare V3, V6 and V7 feature representations, training configurations and classifier metadata.
1.3	Verify that training and live webcam feature extraction produce exactly the same features in the same order.
1.4	Inspect the saved .pkl models and JSON metadata to verify their compatibility.
1.5	Compare model performance using existing evaluation results and identify any testing limitations.
1.6	Select one production candidate while keeping V6 as the full-data baseline.

Expected result:
- Selected model for the first production pipeline.
- Verified feature extraction compatibility.
- V3/V6/V7 comparison report.
- Known compatibility issues documented.
Decision: V6 remains our baseline; V3 and V7 remain comparison candidates. We will not select a model based on accuracy percentage alone.
Phase 2 — Clean up V1–V5
Objective: Preserve useful research while making the active Model A pipeline easier to maintain.
Task	What we are going to do
2.1	Review V1–V5 feature engineering and identify useful improvements.
2.2	Preserve useful classifier comparisons and training experiments.
2.3	Review webcam versions for useful camera handling, confidence and temporal-stability improvements.
2.4	Identify obsolete scripts, duplicate implementations and old paths.
2.5	Archive obsolete experiments without deleting research history.
2.6	Establish one active inference pipeline and clearly document the archived versions.

Expected result:
- Cleaner Model A folder.
- Research history preserved.
- One clearly identified active inference implementation.
- No unnecessary duplicate production code.
Phase 3 — Test RTMPose
Objective: Determine whether RTMPose offers a meaningful improvement over our existing MediaPipe system.
Task	What we are going to do
3.1	Set up RTMPose separately from the existing Model A pipeline.
3.2	Verify that it detects the required 21 hand keypoints.
3.3	Measure CPU inference speed on our available hardware.
3.4	Compare detection reliability under different lighting, backgrounds and hand positions.
3.5	Check whether its landmark representation can work with our feature-extraction pipeline.
3.6	Compare the results against MediaPipe.

Expected result:
- RTMPose vs MediaPipe benchmark.
- CPU performance report.
- Detection reliability comparison.
- A documented decision on whether to retain MediaPipe or switch.
Decision: MediaPipe remains our default unless RTMPose demonstrates a measurable advantage. We will not interrupt the main development just to experiment with another detector.
Phase 4 — Support One-Hand and Two-Hand Recognition
Objective: Understand and extend hand detection according to the actual alphabet-recognition requirements.
Task	What we are going to do
4.1	Identify whether the current system detects the left hand, right hand and no-hand states correctly.
4.2	Test how the system behaves when both hands appear in the camera.
4.3	Determine which target alphabet signs require one hand and which require two hands.
4.4	Design a compatible two-hand landmark representation if the target dataset requires it.
4.5	Collect or verify suitable two-hand training examples.
4.6	Train and evaluate the two-hand extension separately without damaging the working one-hand model.

Expected result:
- Reliable one-hand detection.
- Clear left/right/both/no-hand handling.
- Two-hand recognition design and dataset assessment.
- Separate two-hand model or extension if justified.
Decision: We will first complete the one-hand alphabet experience. Two-hand recognition will be developed according to the actual sign-language scope and available examples.
Phase 5 — Improve Alphabet Accuracy
Objective: Evaluate how reliably Model A recognises alphabet signs in realistic conditions.
Task	What we are going to do
5.1	Evaluate accuracy, precision, recall and F1-score.
5.2	Generate and analyse the confusion matrix.
5.3	Identify frequently confused letters.
5.4	Test difficult letters using the actual webcam.
5.5	Test different users, camera distances, lighting and hand orientations.
5.6	Identify motion-based letters such as J and Z that need temporal recognition.
5.7	Develop and evaluate temporal recognition for J and Z separately.

Expected result:
- Complete model evaluation report.
- List of confusing letters.
- Real webcam testing results.
- Documented limitations and improvement priorities.
Decision: We will not treat a high training or random-split test accuracy as proof of real-world accuracy.
Phase 6 — Build Letters into Words
Objective: Convert individual alphabet predictions into usable text.
Task	What we are going to do
6.1	Implement stable letter recognition before committing a character.
6.2	Prevent repeated letters caused by holding the same handshape.
6.3	Implement cooldown and debounce logic.
6.4	Add space functionality.
6.5	Add delete-last-character functionality.
6.6	Add clear-text functionality.
6.7	Implement word boundaries and text-buffer management.

Expected result:
- Stable alphabet input.
- No accidental repeated letters.
- Working space, delete and clear controls.
- Ability to build words from recognised alphabets.

Phase 7 — Build Words into Sentences
Objective: Extend the text-building system to manage complete sentences without changing the user's intended message.
Task	What we are going to do
7.1	Implement a sentence buffer.
7.2	Define sentence-ending and punctuation rules.
7.3	Manage spaces and word boundaries.
7.4	Investigate optional language correction or suggestions.
7.5	Keep language correction separate from sign recognition.
7.6	Ensure the system never silently rewrites the user's intended message.

Expected result:
- Sentence-building functionality.
- Punctuation and spacing rules.
- Optional language assistance.
- Original recognised text remains available.

Frontend delivery — Included in Phase 8
The frontend is not a separate project. It is the user-facing part of the Model A completion work.









1. Sign to Text
- Live camera recognition.
- Predicted alphabet and confidence.
- Stable recognition indicator.
- Text buffer and sentence display.
- Space, delete and clear controls.
- Optional speech output later.












2. Learn
- Alphabet selection.
- Sign demonstration/tutorial videos.
- Hand-position explanations.
- Replay and learning progress.












3. Practice
- Select an expected alphabet.
- Display its tutorial.
- Capture the learner's hand.
- Compare the stable prediction with the expected letter.
- Correct/try-again feedback.
- Progress tracking.



Practice feedback initially means that Model A recognised the expected letter. Detailed hand-posture scoring would be a later enhancement.

Additional frontend requirements:
- Responsive desktop and mobile design.
- Camera permission handling.
- Camera start/stop functionality.
- Backend connection and loading states.
- Clear error messages.
- Consistent HandLex theme and navigation.

Priority: what must be completed first?
Not every phase has equal priority for the first working release.
Priority	Phases	Reason
Critical	1, 2, 6, 8	Reliable model, inference, text input and frontend integration
Important	5, 7	Accuracy evaluation and sentence-building
Research / extension	3, 4	RTMPose and expanded two-hand recognition

Phase 3 and Phase 4 remain in the roadmap. We will not let optional research block the initial working one-hand experience.
Final completion criteria
By the end of this work, we want to demonstrate the following:
Sign to Text
- [ ] Camera recognises supported alphabet signs.
- [ ] Stable letters are committed once.
- [ ] Multiple letters form words.
- [ ] Spaces and deletion work.
- [ ] Sentence buffer works.

Learn
- [ ] Alphabet tutorials are available.
- [ ] Demonstrations and explanations display correctly.

Practice
- [ ] Learner can select a target alphabet.
- [ ] Camera recognises the learner's attempt.
- [ ] Correct/try-again feedback works.

Technical completion
- [ ] Backend and frontend communicate reliably.
- [ ] Camera and API errors are handled.
- [ ] Model performance is evaluated and documented.
- [ ] Final architecture and limitations are documented.
